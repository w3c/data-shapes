### Consensus and escalation

* What constitutes task force consensus?
* At what point do we conclude that consensus cannot be reached?
* When and how should an unresolved question be escalated to the WG?

**Proposed approach:** We should first attempt to resolve disagreements within the task force through focused GitHub issues. Because substantive discussion will now be recorded in GitHub, co-chairs and WG members can participate there before any formal escalation.

Formal escalation should occur when the task force has identified a specific question that it cannot resolve internally and needs a WG decision.

Issue https://github.com/w3c/data-shapes/issues/1083 now covers several distinct questions and is no longer well suited to focused discussion. We should create separate issues for the remaining points of disagreement, with each issue clearly stating the question to be resolved, the relevant use cases, and the competing arguments.

This will also make any eventual escalation easier for the WG to understand and decide without requiring members to reconstruct the full history of https://github.com/w3c/data-shapes/issues/1083.

### Pull request process

#### Review time

* How much review time should normally be allowed?

**Proposal:** For substantive changes, reviewers should normally be given up to two weeks to review, unless they indicate earlier that their review is complete. Editorial or otherwise non-substantive changes should not require the same review period.

#### Blocking reviews

* What constitutes a blocking review?
* What information must accompany a request for changes?

**Proposal:** A blocking review should identify:

* the specific proposed text or behaviour being objected to;
* why it presents a substantive problem; and
* what resolution is being sought.

The substantive argument should be recorded directly in the PR or linked GitHub issue.

#### Merging with unresolved issues

* When may a PR be merged despite an outstanding disagreement?
* When should the PR remain blocked, be revised, or have the disagreement handled separately?

**Proposal:** Prefer resolving substantive disagreements before merging. Where this is not practical, isolate the unresolved matter in a focused GitHub issue and, where useful, add an `EDITOR NOTE` to the document linking to it.

Where the disagreement concerns whether additional normative behaviour should be specified at all, prefer the less prescriptive wording until there is consensus for stronger requirements.

Unresolved issues should not prevent unrelated agreed work from progressing.

#### Objections raised during meetings

* How should objections raised verbally in meetings be recorded?

**Proposal:** The scribe should record substantive objections in the meeting minutes. The participant raising the objection is responsible for ensuring that the detailed argument is recorded in the relevant GitHub issue or PR.

Meeting participants should review the minutes and correct anything that does not accurately represent their position.

### Working on unresolved proposals

* Can implementation or specification work proceed while the underlying issue remains unresolved?
* How should exploratory work be distinguished from agreed specification changes?

**Proposed approach:** Create a narrowly scoped GitHub issue explaining the proposal, rationale, and relevant use cases. Where useful, create a draft PR so that task force members can review a concrete proposal.

A draft PR or experimental branch does not establish task force consensus or create a presumption that the proposed text will eventually be merged into the specification.

### Concrete use cases

* Identify the concrete use cases underlying disputed normative requirements.
* Record those use cases in the relevant GitHub issues.
* Link relevant issues from the specification where editorial tracking is useful.

**Proposed principle:** Proposals for normative requirements should identify the concrete use cases that require those guarantees.

### Specification architecture: core, building blocks and profiles

* What belongs in the normative SHACL UI core?
* What should remain implementation-defined?
* Should SHACL UI define a profile mechanism for stricter interoperability requirements?
* How do profiles relate to the core specification and composable building blocks?
* For useful features that are not yet sufficiently resolved for normative specification, can the Patterns section be used to document and develop them?

**Proposed approach:** Start by identifying the baseline principles on which the task force already agrees and record those as decisions.

For remaining disagreements, create narrowly scoped GitHub issues containing:

* the specific question to be resolved;
* the relevant concrete use cases;
* the competing arguments; and
* the possible resolutions.

Useful but unresolved work may continue through GitHub issues, draft PRs, and the Patterns section without being treated as agreed normative behaviour.

### General working principle

Agreement should be reflected in normative text. Useful but unresolved work can proceed through Patterns, GitHub issues, and draft PRs. Additional normative constraints should be grounded in concrete use cases and require task force consensus.

Unresolved disagreements should be isolated so that they do not unnecessarily block unrelated work.
