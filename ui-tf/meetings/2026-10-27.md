## `shui:hidden`

[PR #1363](https://github.com/w3c/data-shapes/pull/1363)

**Discussion:**

- **Daniel:** It is generally not desirable for conditional fields to be both hidden and excluded from validation.
- **Edmond:** We should follow SHACL Core semantics.
- **Daniel:** `sh:deactivated` affects how shape targeting works.
- **Ieben:** Agrees with the reasoning.
- **Bergi:** Agrees that we should not redefine `sh:deactivated`, as its semantics are already defined in SHACL Core.
- **Edmond:** We should explicitly state somewhere that SHACL UI follows SHACL Core semantics, including shape targeting and `sh:deactivated`.

**Outcome:** Agreement that SHACL UI should build on the existing semantics of SHACL Core rather than redefine them.

**Action:** Add a section to the specification clarifying that SHACL UI builds on and follows SHACL Core semantics.

## Property Shapes Without Constraints

[Issue #1231](https://github.com/w3c/data-shapes/issues/1231)

**Discussion:**

- **Bergi:** This should be addressed through shape or widget scoring. There should be a default widget for viewing, but not necessarily for editing. `TermViewer` could serve as the fallback.
- **Daniel:** In view mode, this is less of an issue because the existing data provides enough information to select an appropriate widget.
- **Edmond:** We should avoid specifying a fallback widget, as doing so could unnecessarily constrain implementations and future RDF extensions, including potential new RDF term types.
- **Ieben:** Suggests adding a non-normative note acknowledging this case.
- **Bergi:** Agrees that a non-normative note is sufficient and could clarify that fallback behaviour is implementation-specific.

**Outcome:** General agreement to leave fallback behaviour to implementations, with a non-normative note acknowledging the case.
