### Draft proposal on `sh:order` semantics

* Reviewed the draft proposal: <https://docs.google.com/document/d/1aXv_B20fd1E1MQGUm_XqI_9caVZQh981tBRwx3ls4-0/edit?tab=t.0>.
* bergi argued that the tie-breaking algorithm should be specified as a **SHOULD** rather than a **MUST**, since fully deterministic ordering is only achievable when all properties have distinct `sh:order` values.
* Daniel expressed a preference for deterministic behavior even when duplicate order values are present.
* bergi suggested requiring implementations to provide a tie-breaking algorithm, while only recommending a specific algorithm in the specification. This would preserve implementation flexibility while maintaining deterministic behavior within a given implementation.
* Daniel and Ieben noted that this approach would still result in non-deterministic behavior across different implementations.
* bergi emphasized the importance of finding wording that allows existing implementations to remain compliant with the specification.
* Daniel reiterated that deterministic behavior is important for achieving the intended goals of a specification.
* The task force decided to postpone a decision until the next meeting.
* A possible compromise is:
  * Implementations **MUST** implement a tie-breaking algorithm.
  * Implementations **SHOULD** use the tie-breaking algorithm recommended by the specification.
* **Action:** Further reflection and collection of use cases are needed before reaching a conclusion.

### Multiple entities support

* Ieben: Discussed whether UIs should support rendering multiple entities when a NodeShape matches multiple resources and no focus node is explicitly provided.
* bergi supports adding support for rendering all matching entities.
* Ieben raised the concern of how a renderer should otherwise decide which matching entity to select as the focus node.
* Daniel previously explored a UI pattern where a selection list allows the user to choose a focus node:
  * <https://storybook-shacl-renderer.shapething.com/?path=/story/capabilities-form--multiple-forms-edit>
  * The prototype supported both view and edit modes.
* Daniel later moved away from this approach.
* The topic requires additional discussion and will be revisited in a future meeting.
