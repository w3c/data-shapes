## Scoring algorithm

**Ieben:** Caught up with Robert to discuss the details of the scoring algorithm.

**Robert:** Wasn't part of the task force when the algorithm was originally developed, so the discussion was primarily informational. Found the algorithm difficult to read and understand, which is a concern if we publish it in its current form.

**Bergi:** Proposed renaming the section to "Widget Selection" and introducing widget pinning, with the scoring algorithm serving as a fallback when no widget is pinned. This should improve readability.

**Daniel:** Supports "Widget Selection" with two sections: pinning and scoring. Suggested presenting scoring first.

**Daniel:** Questioned the rationale for removing `shui:widget` in favour of `shui:viewer` and `shui:editor`.

**Bergi:** Argued that separating these properties follows better modelling practices, similar to the distinction between node and property shapes in SHACL.

**Edmond:** Suggested simplifying the scoring algorithm where possible and delegating certain responsibilities to existing RDF processing mechanisms (see GitHub issue comment).

### Key discussion points

- **Readability:** Improve the widget selection algorithm section for readability.
- **Widget properties:** Consider `shui:widget` versus separate `shui:viewer` and `shui:editor` properties.
- **Accept matcher:** Explore an approach similar to TypeScript's type system for validating incoming data against a widget's requirements, rather than relying on a class hierarchy that is difficult to maintain.
- **Score preprocessing graph:** Further discuss the role of graph preprocessing in scoring.
