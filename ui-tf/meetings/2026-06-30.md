## Recommendation Progression

The group discussed the expected path towards Recommendation.

SHACL UI is currently in wide review. The next steps are to address comments and feedback, establish the implementation report, define test cases, and gather implementation evidence.

The First Public Working Draft is underway. Progression from First Public Working Draft to Candidate Recommendation requires a formal Working Group vote. Progression from Candidate Recommendation to Recommendation depends on implementation evidence.

### Action

* Establish a SHACL UI feature set with stable identifiers, and potentially associated test cases. This work will take place over the coming weeks and months.

## `sh:order`

Task Force members each discussed their interpretation of `sh:order`.

The group agreed that the specification should avoid being overly restrictive or locking in semantics prematurely.

Bergi’s interpretation appeared to cover most, if not all, of the interpretations raised by the group. Bergi noted that the Task Force should avoid constraining `sh:order` too much, so that its semantics can still be extended or refined in future if new use cases emerge.

Ieben asked the Task Force for views on the semantics of `sh:or` when used with `sh:order`, referring to SHACL Core Example 52.

This reminded the group that logical constraints such as `sh:or`, `sh:and`, and related constructs still need to be addressed. There is prior art in the DASH form generation documentation.

Daniel mentioned that, based on his previous experience, it may be preferable to restrict the use of `sh:or`; otherwise, the rendering semantics can become too complex.

### Action

* Ieben to create the first draft of the `sh:order` section.
* Other Task Force members to follow up with edits.
