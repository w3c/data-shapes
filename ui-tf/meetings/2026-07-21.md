## How open or prescriptive should the SHACL UI specification be?

**Bergi:** We should clarify what implementers should expect from the specification so that this question does not need to be revisited repeatedly. As a general principle, the specification should remain open where prescriptive requirements would prevent otherwise valid use cases.

**Edmond:** New features and use cases could initially be documented as patterns, then later promoted to normative requirements if necessary. This would defer the decision about whether a feature should be mandatory without blocking contributors from documenting and progressing the work.

**Daniel:** This is challenging because we are writing an interoperability specification, not simply a collection of patterns. That does not mean every aspect must be fully deterministic, but some of the rules proposed in the GitHub issue appear too narrow. Profiles may provide a way forward by allowing implementations to declare which parts of the specification they support. For example, some implementations may not render every property on screen or may use different field-ordering behaviour.

**Bergi:** The specification should focus on reusable building blocks that implementations can combine as needed. It should not prevent legitimate use cases. For example, the proposed default behaviour for `sh:order` does not reflect how most existing implementations behave: many place values without an explicit order at the end rather than in the middle. I have also previously raised the closed-world use case described in the blog post, which the current scoring algorithm does not support.

**Daniel:** The specification is ultimately the contract with implementers and users. Openness is a useful general guideline, but individual features still need to be evaluated on their merits. In general, behaviour should be deterministic where appropriate and extensible through well-defined extension points. The widget mechanism is a good example because it defines interoperable behaviour while remaining pluggable.

**Bergi:** When a `MUST` requirement prevents a valid use case, there should be a clear justification for retaining it. I would like the group to establish a process for handling this. Edmond’s proposal to initially describe features using `SHOULD` or `MAY` could help avoid repeatedly revisiting the same discussion during meetings.

**Daniel:** I am open to defining a different process. However, I also want to note that Bergi previously suggested discussing proposals in the task force before opening GitHub issues, partly because broader Working Group discussion might derail the conversation. I do not support requiring task-force discussion before an issue can be opened.

**Robert:** User interfaces are difficult to formalise precisely. I would prefer the specification to remain open and configurable rather than attempting to prescribe every aspect of UI behaviour. There is also less direct interoperability between user interfaces than there is in other parts of SHACL.

**Daniel:** The strength of the interoperability guarantee will depend on what vendors agree to implement. In this context, the specification provides a promise about what users can expect when supplying particular data and shapes, even if that promise is less strict than in other SHACL specifications.

**Bergi:** When discussion of a `MUST` requirement becomes blocked or prolonged, we should move the discussion from the meeting to a GitHub issue.

**Action:** Group members to reflect on and comment on the relevant GitHub issue.

## Conflict resolution for property UI components

**Daniel:** I have implemented a conflict-resolution approach for property UI components:

https://github.com/ShapeThing/SHACL-renderer/blob/feature/node-and-property-ui/lib/helpers/propertyPointerConflictResolution.ts

I would like feedback from the group.

**Bergi:** I have opened a similar issue for `shacl-engine`. Is this also relevant to validation? It may be more appropriate to address the underlying behaviour in SHACL Core.

**Daniel:** From my perspective, the issue has now surfaced in SHACL UI. It sits between validation and form generation. I am not certain whether it belongs in Core because it could also be treated as an optimisation step.

**Bergi:** All constraints still apply, but constraints such as minimum and maximum counts may be simplified during optimisation. I can prioritise this as a SHACL Core issue and determine whether resolving it there also addresses the UI case. There may also be related complications. For example, `sh:closed` was previously treated only as a Boolean value, but it can now be represented as an entity with an `rdf:type`.

**Daniel:** I had considered documenting this as a pattern or adding a dedicated section to the SHACL UI specification. However, I understand Bergi to be proposing that we first address it in SHACL Core. I am comfortable with either approach.

**Bergi:** There appear to be several edge cases, so I would prefer to clarify the behaviour in SHACL Core first. The same optimisation rules would then apply consistently to validation and UI processing.

**Example:** If one property shape specifies `sh:minCount 1` and another applicable property shape specifies `sh:minCount 2`, an optimisation step could remove the weaker, redundant constraint.

**Action:** Bergi to investigate the issue in SHACL Core and open a GitHub issue or start the relevant discussion.

## SHACL Renderer without a focus node

**Bergi:** This topic was discussed early in the work. The original position was that a SHACL Renderer always receives a focus node, but the current proposal introduces support for rendering when no focus node is provided.

https://github.com/w3c/data-shapes/issues/609#issuecomment-4992288075

The use case appears to involve discovering focus nodes from SHACL targets and then rendering without a single predefined focus node, potentially with multiple value nodes returned by target evaluation.

**Daniel:** In a system such as a CMS, these may be represented as two separate pages or steps. Ieben described a use case where users can switch between value nodes. I have implemented something similar in one of my projects, where users can switch between available nodes.

**Bergi:** We should cover the case where multiple candidate nodes are available.

**Daniel:** Let us revisit this next week when Ieben is present and respond to his comment on the issue.

**Action:** Group members to review and respond to the GitHub issue.
