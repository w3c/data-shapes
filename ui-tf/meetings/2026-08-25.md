Issue #1164 — [UI] Decision: what does a conformance claim guarantee, and do claims name what they cover?

Ieben: Said the question needed to be put to a Working Group vote because an objection had been raised. He framed the question as whether SHACL UI features should be divided into conformance classes.

Daniel: Said the group needed to decide whether it wanted this conformance model and whether it should be published in the specification. He framed the underlying question as whether SHACL UI should define a small normative core or a set of building blocks.

Robert: Said he was somewhat sceptical about applying this model to UI, but was not opposed to it.

Bergi: Referred to the existing profiles issue. He said he was not blocking the work but believed profiles were the main mechanism through which conformance should be addressed and suggested discussing it there.

Ieben: Responding to Robert's question about testability, said implementations would not be required to adopt the test suite, although having a conformance test suite would be recommended. He said there needed to be a base set of conformance requirements and proposed translating the feature definitions into tests. He also noted that Eliana had expressed support for this approach the previous week.

Ieben: Said there had previously been a shared understanding that the group should first define the features in the specification and then decide whether profiles were necessary.

Robert: Agreed that a test suite would be useful for a reference implementation, but asked how UI behaviour could be tested when other SHACL test suites operate on RDF data.

Bergi: Said he had defined concepts rather than features. He thought the table was useful work, but said it should be mapped against use cases before deciding how fine-grained the definitions should be.

Ieben: Pointed to issue #1165. He said he did not think the visual UI itself should be tested and suggested that a JSON AST representing the UI could provide a UI-agnostic rendering model.

Daniel: Said the conformance model should not dictate the UI and noted that such a model could also make the specification easier for AI systems to work with. He said his concern was largely practical and that he was not sure implementers would actually follow the conformance requirements.

Bergi: Asked that the meeting notes record his statement that Ieben had said during the call that he was not listening to Bergi's comment.

Bergi: Asked how the group should proceed and whether the question should now go to the Working Group.

Daniel: Asked Robert whether his concerns related to an implementation he planned to build or to implementations in general.

Robert: Clarified that he was speaking about implementations in general and was not opposed to the proposal.

Daniel: Said that clarified that they were on the same page.

Ieben: Agreed that implementers should not be forced to run conformance tests. He said the tests and feature table should instead guide implementers by making it clear which features they support. This could also allow subsets of features to be defined and implementations to indicate which ones they support.

Edmond: Suggested putting the question in the chat and holding a vote there.

Ieben: Said a Working Group vote was required, which was why he had raised the issue during the meeting.

### PR #1180 — First draft of shui:readOnlyGraph

Robert: Raised the global configuration discussion and said he had created a new issue after the previous PR was automatically closed. He asked whether a read-only graph was really needed, explaining that his main use case was inference data.

Ieben: Agreed that the specification could benefit from a read-only graph, including for the use cases Edmond had raised. His question was whether it needed to be represented as a global configuration parameter.

Robert: Said that the shapes graph and data graph were already represented in the vocabulary, so it could make sense to define the read-only graph there as well. He noted that SHACL currently cannot distinguish between read-only and editable data because there is only one data graph.

Ieben: Proposed updating the relevant algorithm so that it operates over both the data graph and the read-only graph.

Robert: Agreed with the direction but asked whether that would require changing SHACL Core.

Daniel: Said he would also be comfortable treating the read-only graph as a parameter to the SHACL Renderer. He noted that this could become difficult when dealing with large graphs.

Ieben: Said there could be pushback against changing SHACL Core and suggested that the concept could instead be defined solely in SHACL UI.

Robert: Raised a backwards-compatibility concern if the change were made in Core and said SHACL UI alone might not provide enough justification for such a Core change.

Edmond: Said the data graph should remain a conceptual construct and that a concrete data graph could, for example, be the conjunction of two or more graphs. This is how it's used in SHACL Core.

Daniel: Proposed representing the read-only graph as a set of named graph IRIs.

Edmond: Said it would still be useful to define the concept in SHACL UI so that SHACL UI algorithms can refer to it.
