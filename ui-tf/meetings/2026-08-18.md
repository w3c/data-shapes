### SHACL UI Profiling

**Bergi:** Based on building blocks, profiles specify strict subsets or combinations of features.

PR: [#1132](https://github.com/w3c/data-shapes/pull/1132)

**Bergi:** People should use profiles for conformance, but this should not be strict yet because we have not defined how conformance is tested in SHACL UI.

**Robert:** Are profiles defined by use case, or are they defined by the UI Task Force?

**Bergi:** Users can still define their own profiles based on their use cases.

**Ieben:** I like the idea that the Task Force defines profiles that others can use. We previously also defined features, which I liked, and those could form part of the profiles. Is there a way for me to create a subprofile and add more features to it?

**Daniel:** I'm wondering whether profiles are the right approach. Given all the possibilities, it will be difficult to standardise them. For example, providing seven options would be too much. My proposal is that the upper edge may remain undefined—for example, pattern-related features—while the lower boundary has a normative specification. I would therefore like to start with a small core UI profile.

**Bergi:** With the features proposal, the idea is to capture features as concepts within a profile. My intention is not to create a large number of profiles. Everyone should align with the profile while specifying which concepts they support. I am happy to work on the core UI profile.

**Ieben:** It's good to hear that the features proposal is moving in the right direction. I wonder what the value of profiles is, though, because adding or removing a feature effectively creates another profile. What if we instead have a table of features and implementations can indicate which ones they support?

**Nick:** Other specifications use conformance classes. These could be IRIs representing features in SHACL UI. A conformance class is closer to the table of features and tick boxes Ieben mentioned. In GeoSPARQL, for example, conformance classes show how much of GeoSPARQL an implementation conforms to, rather than saying that it either conforms completely or does not conform because it is missing a few features. Profiling is generally more about tightening an existing standard by mandating particular properties or behaviours. I think you're all essentially right that a profile is a bundle of features or concepts.

**Robert:** Having predefined profiles makes sense when there are many features. How are the individual features formalised?

**Bergi:** They are defined in the specification.

**Daniel:** Ieben, are you still in favour of a small normative core?

**Ieben:** Yes. For example, a tie-breaking algorithm could be defined as a feature, and an implementation could state that it conforms to that feature.

**Daniel:** I think there is quite a bit of overlap between what Ieben and Bergi are proposing. Bergi, are you still in favour of a small normative core?

**Bergi:** Yes. The features and concepts would be defined in the specification so that they can then be bundled into profiles.

**Ieben:** I think we are converging. The biggest remaining difference is around when an implementation can claim conformance. I still want there to be a required set of features that must be implemented before something can claim conformance to the SHACL Renderer. This is probably the main point we need to discuss and agree on.

**Eliana:** I think having a base set of features that an implementation must support before calling itself compliant is quite important. A custom profile would still be possible, but it may not be adopted by the wider community.

**Robert:** What would the default profile be?

**Bergi:** Just to mention, there is now RDF-star. We can take a pragmatic approach.

**Ieben:** We could consider a compliance profile that defines the set of features required for compliance. We should discuss whether we want to define profiles or conformance classes, but first we should define the features themselves.

**Nick:** Regarding #1142 and Bergi's use case: if that is an important use case, I previously thought my use case was part of it as well. I've added a comment describing how we could indicate the use case and conformance—for example, a tool that I implement could state what it conforms to. What's important is the overriding mechanism, such as in the `sh:order` case. We may be overanalysing features and profiles. Fundamentally, we want to state what a UI engine supports. On reflection, I'm also supportive of stricter behaviour in SHACL UI.

**Bergi:** There are some things, such as ordering, where making a behaviour mandatory could rule out other use cases.

**Nick:** If profiles and conformance classes are only needed to deal with `sh:order` and a couple of other behaviours, perhaps those behaviours should simply be represented in the data.

**Daniel:** Regarding the scoring system and ordering, I don't fully understand why they would not be implemented for a customer or a potential future project involving a closed-world use case. The arguments I've heard don't seem to boil down to functional requirements. I propose that a use case should explain, in specification terms, why the current ordering proposal does not work. Implementers can choose whether or not to implement it. With the scoring system, we have closed- and open-world situations and schema exchange, and I've tried to identify when a scoring system is useful. I'm trying to understand the argument for not wanting a scoring system because of a particular use case or because there are no schema changes. For me, the scoring system is required. We must always render SHACL shapes and validate them with a SHACL processor. I understand the argument that the scoring system may be too complicated, but I still think it should be required.

**Bergi:** Validation can happen on either the client or the server, but the scoring system requires a SHACL validation engine on the client.

**Ieben:** In response to Daniel on ordering and the scoring system: in issue [#1162](https://github.com/w3c/data-shapes/issues/1162), I proposed a solution that weakens the specification. I've also left a comment on #1163.

**Daniel:** How do we resolve the deadlock? Do we bring it to a vote?

**Nick:** At a minimum, we should give the Working Group a week before bringing it to a vote.

**Robert:** I agree with Edmond that it is still not clear what the arguments on both sides are.

**Ieben:** For votes, are they always Working Group votes, or can they happen within the Task Force?

**Nick:** I don't think that is well defined. We should first try to resolve the issue internally before escalating it to the Working Group.
