## SHACL Core Constraints for UI

Discussion:

The group agreed to create a matrix comparing SHACL Core constraints that are directly mappable to widgets against those that are not. For directly mappable constraints, expected widget behaviour should be explicitly defined. For non-direct mappings, the UI implications and validation behaviour must be clarified.

Special focus areas include consistent handling of sh:minCount and sh:maxCount, including how cardinality constraints affect rendering and interaction. A conformance-oriented test suite was identified as necessary to ensure consistent behaviour across implementations.

For sh:or, Daniel will add further thoughts to issue 533 to clarify how disjunction should influence UI rendering and selection logic.

## shui:editor

Status: Scoring remains a MUST (to be reflected upon later)

1. Scoring System: MUST or SHOULD?
Discussion:
-	Bergi: Proposed making the scoring system and accept function a SHOULD rather than a MUST to support additional use cases, including IoT scenarios where all shapes are sh:closed. Referenced the Netflix UDA article (https://netflixtechblog.com/uda-unified-data-architecture-6a6aee261d8d) as an example of architectural flexibility.
-	Daniel: Noted that scoring aligns more naturally with OWA models, while in CWA contexts (e.g., sh:closed shapes), scoring may be less important.
-	Ieben: Observed that if scoring is only a SHOULD, every shape would effectively require a shui:editor to guarantee interoperability across implementations.
-	Conclusion: Keep scoring as a MUST for now and revisit later if needed.

2. Shapes vs. Non-Shapes Approach
Stances:
-	Bergi: Favours the Non-Shapes Approach to avoid runtime complexity and bypass scoring when a widget is directly assigned. The non-shapes approach can take the pointer directly without performing score calculation.
-	Ieben: Raised whether skipping scoring should be optional and explicitly mentioned in the spec.
-	Daniel: Questioned whether the accept function would still be required even if scoring were optional. Also raised concerns about handling cases where no clear “happy path” exists.

Open question: If scoring is optional, how does that affect the semantics and guarantees of shui:editor?

3. Semantics of shui:editor
Discussion:
-	Bergi: Concerned that if a widget is explicitly assigned via shui:editor but not selected due to SHACL violations, and a fallback widget is rendered via scoring, this becomes confusing and hard to debug.
-	Daniel: Noted that in DASH this corresponds to a “preferred” editor, and argued that falling back to scoring is correct behaviour.
-	Ieben: Suggested defining semantics first, then deciding on naming.
-	Proposal: Treat shui:editor as assigning a very high score rather than bypassing scoring entirely.
-	Daniel: Suggested potentially introducing both shui:editor and shui:preferredEditor to distinguish strict versus preference semantics.

Summary: Open widget scoring as a SHOULD was considered to support additional profiles and use cases, but time constraints limit exploration of alternative profiles at this stage.
