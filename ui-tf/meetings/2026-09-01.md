## Profiles and conformance

### PR #1083

**Bergi:** PR #1083 demonstrates how we could define profiles and compose concepts together.

**Nick:** A few of us have commented on #1173, and Carine has agreed with the proposal in the PR. Bergi, one of your concerns is how the use cases are linked to the feature list and, in particular, how they link back to the requirements.

**Bergi:** My main concern is putting this into the specification.

**Nick:** If we can revisit the linking outside of the specification, we can come back to this and add the links.

**Daniel:** I want to note that Carine has stated that conformance classes are not something we should look into at this stage. I share this conclusion. We should go with whatever the W3C requires.

**Bergi:** I think the features are currently too fine-grained, and they do not reference the exact parts of the specification they relate to.

**Daniel:** I agree that we can make them somewhat coarser in terms of granularity. Carine has also said that we should use the term "feature", as defined by the W3C.

**Nick:** To summarise, we do need the use cases, but they need to be coarser than they are now. The things that matter need to link to the use cases and the relevant parts of the document. I also think using the term "feature" is the correct way to go, especially given how widely the concept is already used in the Semantic Web community.

### Do we agree that, in the context of this PR, "concept" and "feature" refer to the same underlying idea?

**Bergi:** I disagree. I do not think they refer to the same underlying idea.

**Daniel:** I think we should conform to the W3C's use of the term "feature".

**DECISION:** Use the term **Feature**, as defined by the W3C.

### Do we agree that the current feature list, together with the proposed conformance levels, provides a conformance mechanism?

**Nick:** Does it provide a mechanism? Yes. However, the specific features still need to be established.

**Bergi:** I am okay with how the levels are defined, as well as with the feature list. I agree with the feature table and the conformance-level column.

**Daniel:** I am wondering why Carine has said that we should not resolve the conformance question yet.

**Robert:** I am also a bit concerned about the topic of conformance. I am not sure that it makes sense for UI. If we make conformance difficult to achieve, it could negatively affect implementations. I do not have a proposed solution, but I wanted to raise the concern and say that I would prefer a simple approach. I would prefer the feature table over introducing profiles.

**Daniel:** Conformance and interoperability are closely related, but my understanding from Carine is that conformance is not currently a priority for the W3C, whereas interoperability is. She has said that there are misunderstandings around this topic, and I think there are misunderstandings on both sides of the argument. Perhaps we should not deal with conformance now and should instead focus on interoperability. We could use normative text within the relevant sections rather than defining a feature list.

**Nick:** There may be dependencies within the normative text. There should be a core and then a set of satellite modules.

**Bergi:** If we say that we have features, then we can say that implementations conform to those features. I do not see a technical problem with that. We may decide not to use profiles, but an implementer could instead state which features they support.

### If not, what additional mechanism is needed, such as conformance classes or profiles, and what problem would it solve?

**Daniel:** I do not think we should talk about profiles at this stage. I also do not think Carine has suggested profiles; I think she has suggested quite the opposite. We can have a more thorough discussion later to determine what is required.

**Bergi:** If we do not define profiles now, we still need to clearly define the features and what conformance to an individual feature means. That has implications for the wording throughout the rest of the specification.

**Daniel:** If I understood Carine correctly, she was saying that interoperability is important and that normative terms such as MUST, MAY and SHOULD apply only within the context of the particular features being implemented.

**Nick:** There are currently around 30 features. That may be too granular, but we could revise the list down to around 15. I think we are getting close. We can do this in stages and determine the groupings later.

**Daniel:** I like that structure. However, there is still a deadlock around Bergi's use case. I propose that we defer that question, but we then need to determine how we write the text and continue our work in the meantime. I think that is the problem we should focus on.

**Bergi:** I do not want to work on a specification where my use case is not covered, which is why I would like to resolve this now rather than defer conformance until later. I am open to how we define it, but I do not want to postpone it.

**Daniel:** I think that leaves us in a position where we may need a vote to resolve this. We should consult Carine and other W3C members about how conformance should be handled. There are W3C requirements intended to ensure interoperability.

**Bergi:** My proposal is to define a minimum profile. I feel that I am already making a lot of compromises. The specification would recommend using profiles.

**Edmond:** If we make certain features recommended rather than required, do we still need profiles?

**Bergi:** Yes.

**Edmond:** The crux of the issue seems to be that some features would be required, while others would only be recommended.

**Daniel:** We should create a PR to remove normative text that says implementations must implement all features. At a later stage, when we deal with conformance, I can state my use case and you can state yours.

**Bergi:** We should clarify now what the process is for achieving interoperability.

**Daniel:** I think the next step should be to consult Carine.

**Robert:** The Core specification does not say that an implementation implements all constraints, but at the same time it would not make sense to implement only half of it. So I am a little confused about how this should work.

**Nick:** Bergi, for your use case, you do not want scoring to be required, but in the end there may only be one or two features where our requirements differ. We should consult Carine next Monday.

**ACTION:** Consult Carine on how conformance should be defined and whether the detailed conformance mechanism can be determined at a later stage.
