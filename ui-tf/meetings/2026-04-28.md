## Label Resolution

Bergi is working on label resolution. There are two separate cases to consider:

* Labels for property paths.
* Labels for value nodes.

Robert asked whether this could be handled through global configuration.

Edmond suggested that global configuration could allow implementations or users to override the label predicate used for property path labels.

Robert noted that this would likely need to support a list of properties with priority ordering. He is currently working on the global configuration proposal in https://github.com/w3c/data-shapes/issues/869.

Robert suggested defining two separate configuration properties for label resolution: one for property paths and one for value nodes.

Bergi asked whether the property path configuration should support sequence paths.

Daniel noted that SKOS-XL requires an additional hop, so sequence paths are needed for that use case.

Robert observed that support could become more complicated if other property path forms, such as inverse paths, are also allowed.

Bergi suggested that, if full property path support is too difficult, the feature could be restricted to sequence paths.

Daniel asked whether node expressions should also be considered in addition to property paths.

Robert suggested that node expressions could be used as a fallback, for example to derive a local name from an IRI.

The group agreed to add configurable property paths for both label resolution cases.

## Global Configuration

Robert supported Holger’s suggestion of dual-typing the configuration resource as both sh:DataGraph and shui:Configuration.

Reference: https://github.com/w3c/data-shapes/issues/869#issuecomment-4323725285

Bergi explained that, in TQ, users work with the concept of an asset collection, which is always represented as a named graph with an owl:Ontology. Because the ontology is always present, the configuration is attached to it.

Bergi also noted that it should be reinforced that there should only be one sh:DataGraph. In TQ, “subgraphs” are modeled using shapes rather than named graphs.

Robert noted that the group had also discussed having a property that links to the global configuration. This would allow configuration retrieval to use the property directly, without depending on a specific subject type.

Robert said that configuration could be included either through the configuration property or through owl:imports.

Edmond suggested that global configuration predicates may be candidates for the W3C registry, alongside widgets and roles.

Bergi provided the following example for discussion:

```turtle
:graph
    a sh:DataGraph, shui:Configuration ;
    shui:config :config ;
    shui:timeZone "Europe/Vienna" .

:config
    a shui:Configuration ;
    shui:defaultNamespace "https://somewhere.com" ;
    shui:config :sysConfig .

:sysConfig
    a shui:Configuration ;
    shui:languagePreference ( "" "en" "de" ) .
```

Daniel raised a concern that supporting both shui:Configuration and shui:config would require implementers to support two configuration resolution mechanisms. Implementations would first need to inspect the data graph itself, then follow shui:config. This also introduces hierarchy handling, because implementations would need to determine which configuration value takes precedence when duplicate properties are present, especially where configuration is imported using owl:imports.

Bergi noted that TQ always specifies an entry point, which is the subject representing either the data graph or the configuration. He suggested keeping this open, or providing suggestions on how the entry point configuration is resolved.

Bergi provided the following revised example:

```turtle
#:graph a sh:DataGraph, shui:Configuration ;
:graph
    a sh:ShapeGraph, shui:Configuration ;
    shui:config :config ;
    shui:timeZone "Europe/Vienna" ;
    shui:widgetSet :myWidgetSet .

:config
    a shui:Configuration ;
    shui:defaultNamespace "https://somewhere.com" ;
    shui:config :sysConfig .

:sysConfig
    a shui:Configuration ;
    shui:languagePreference ( "" "en" "de" ) .
```

And the following illustrative configuration resolution logic:

```js
function resolveConfig(config) {
  return {
    ...localConfig(config),
    ...resolveConfig(config.out(shui.config))
  };
}
const entry = ???;
const config = resolveConfig(entry);
```
