### Simplified UI Scoring

PRs:
- https://github.com/w3c/data-shapes/pull/1273
- https://github.com/w3c/data-shapes/pull/1249

**Daniel:** I suggest that we test only the outputs rather than the internal implementation, provided implementations can achieve the required results efficiently.

**Bergi:** My concern is making the algorithm as reusable as possible. Widget selection must produce the same result across implementations.

**Daniel:** Would implementing Bergi's version result in unnecessary SHACL validations?

**Bergi:** Yes.

**Daniel:** That could be problematic for page load performance, as the additional validations are computationally expensive. Could we find a middle ground? I also prefer the more concise wording in Bergi's proposal.

**Bergi:** My main concern is the duplication.

**Daniel:** I propose adopting most of Bergi's text and adding a non-normative note suggesting how implementations could optimise the algorithm, such as by returning early.

**Bergi:** The current text already states that widget selection might require only the first widget. The specification should not go into implementation details or enumerate possible optimisations.

**Ieben:** Could we collaborate on the wording in a single PR rather than comparing two competing proposals?

**Edmond:** I agree that we should collaborate on a single PR. We should also consider making the text more abstract by avoiding concrete implementation details, such as specific functions, which could imply that implementations must use them. This appears to be the source of the current discussion about duplication and performance when following the algorithm as written.

**Daniel:** Even with my more optimised implementation, widget selection is still slow during page loads. I'm concerned that implementers might perceive the specification as prescribing an inefficient algorithm.

**Robert:** The best approach would be to avoid defining implementation details in the specification. We should not constrain implementations in ways that could make future, otherwise valid approaches non-conformant. We encountered a similar issue with the stratification algorithm in SPARQL-RL.

**Daniel:** Making the algorithm more abstract would address my concerns.

**Edmond:** It would be helpful to consolidate the agreed wording into a single PR so that the remaining contentious points are easier to identify, review, and resolve.

**Action:** Create a GitHub issue for the task force to review both PRs and agree on a consolidated approach.

### Pull Request Procedure

**Edmond:** We should aim to merge PRs promptly once they have received two approvals. Smaller, focused PRs are easier to review and avoid requiring reviewers to follow lengthy discussions spread across multiple GitHub issues and PRs.

PRs should focus on incorporating work that has already been discussed and agreed upon. New ideas and features should first be brought to the task force through GitHub issues and weekly meetings, as we already do. This should help avoid unnecessarily lengthy discussions during PR reviews.

**Robert:** Two approvals are sufficient. The specification is still evolving, and any necessary corrections or refinements can be addressed through subsequent PRs.
