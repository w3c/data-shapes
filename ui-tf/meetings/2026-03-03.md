## shui:editor and shui:viewer: Determinism vs. Flexibility

Discussion:
-	Edmond - Proposed making shui:editor and shui:viewer a MAY to allow implementation flexibility.
-	Ieben - Raised concern that this could lead to non-deterministic rendering outcomes across implementations.
-	Daniel - Noted there are merits to both approaches: either use the scoring system uniformly for everything, or allow those predicates to assign widgets directly without defining score shapes.
-	Bergi - Questioned whether deterministic widget outcomes are strictly necessary, suggesting that as long as users can edit their data, exact widget choice may not matter.
-	Daniel - Argued that the characteristics of shui:editor should be clearly defined so results are predictable. Emphasised the importance of supporting repair mode, where faulty data must still be editable. A strict direct assignment may prevent rendering the correct widget in such cases.
-	Bergi - Asked what happens if an implementation is missing certain widgets.
-	Daniel - Responded that implementors should be expected to support the core UI widgets.
-	Bergi - Maintained that forms should still function even if a particular widget is unavailable.
-	Daniel - Stated that loading established shape sets (e.g., European DCAT-AP and SKOS NL) should generate deterministic forms.
-	Ieben - Added that different implementations should render the same widgets, though styling differences are acceptable.
-	Edmond - Noted that SHACL UI defines a core set of widgets, while implementations may introduce custom widgets (e.g., rendering a GeoSPARQL WKT literal as a map) to override primitives.
-	Daniel - Asked whether an implementation remains spec compliant if all core components are removed and replaced with custom ones.

This led to broader questions:
-	What constitutes spec compliance?
-	Is SHACL UI a spec for a library or for a system?
-	What must be implemented for conformance?
