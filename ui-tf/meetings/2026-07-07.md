## SHACL Rules

Edmond had no specific comments, noting that he does not yet understand SHACL Rules well enough, particularly where inferred triples are generated, to comment on how they affect UI.

Robert explained that the topic is mainly about the interaction between SHACL Rules and validation, and how that interaction might work in a UI context. He noted that there is a read-only aspect and some overlap with node expressions. He also suggested that this is more of a data governance topic. There may be implications for global configuration, such as whether some graphs are read-only, but the model still assumes one data graph. What happens with inferred data is likely implementation-specific.

Daniel noted that some implementers do not use SHACL Rules directly, but instead use some form of AST to generate HTML and SVG.

Daniel asked about the difference between node expressions and rules.

Robert explained that rules are mainly used for data transformation rather than validation. Node expressions are useful when values need to be computed dynamically rather than fixed. Node expressions are coupled with other constraints, whereas rules are an independent rule language.

Bergi added that node expressions can be used to compute values for read-only display, while rules are used to add additional information.

Robert noted that rules may be usable to close or deactivate shapes.

Robert also suggested that, for UI purposes, inferred triples might be displayed and users could be allowed to move those inferred triples into the data graph.

Bergi suggested that inverse links could be created automatically to support navigation between related resources.

Edmond asked when node expressions, rules, and inferred triples should run, and whether the UI specification should define this.

Robert’s intuition was that the UI specification should avoid defining this and leave it implementation-specific.

Bergi agreed, noting that defining this too strictly could trigger expensive computations.

Ieben raised similar concerns to Edmond. He wondered where inferred triples should go, and how they should be displayed or managed in the UI. He also asked whether inferred triples could be edited while they are still in the inferred graph.

Bergi noted that this depends on the use case. Some rules could be defined specifically for the UI, but this would require a well-defined workflow. One simple model is that inferred triples can only be edited once they are moved into the data graph. Another model is that editing an inferred triple automatically adds it to the data graph. The right approach depends on the user’s intent.

Daniel mentioned that he had been thinking about reification and attaching visual properties to inferred statements. In his editor, he has insertions and deletions.

## Logical Constraints: `sh:or`

Ieben raised the question of how `sh:order` should apply in combination with `sh:or` and other logical constraints.

Daniel said he uses `sh:or` on node shapes for conditional fields and mixed datatypes. He suggested that these could be documented as recipes or patterns that implementations may support.

Ieben suggested abstracting this and describing how `sh:or` works with constraints more generally.

Bergi noted that rendering becomes tricky when complex datatypes are involved.

Daniel said he is hesitant about supporting too much complexity, particularly where it is unclear how that complexity translates into a user interface for end users.

Bergi cautioned that the specification should not constrain either simple fixed UI use cases or more dynamic use cases required by systems such as Wikidata.

Ieben noted that this is a trade-off between how technical or RDF-oriented the UI should be. For complex systems such as Wikidata, he agreed that complex logical constraints need to be supported. He mentioned that he has implemented an example for full name handling: https://smessie.github.io/shacl-ui.js/src/cv.html

The group agreed that the specification should provide guidance for implementers supporting `sh:or`.
