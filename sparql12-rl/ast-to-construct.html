This document contains draft text for the appendix "Translation of SPARQL-RL to SPARQL" of SPARQL 1.2 RL.

It gives an algorithm that translates one SPARQL-RL rule into one SPARQL `CONSTRUCT` query, together with the RDF dataset that query is executed over.

This document is not a W3C publication. It is working material for the W3C Data Shapes Working Group, addressing issue #1303.

Translation of SPARQL-RL to SPARQL

This appendix gives an algorithm that translates a single rule into a single SPARQL `CONSTRUCT` query, together with the RDF dataset that query is executed over. Executing the query produces the triples given by evalRule(R, G, GD) of Evaluation of a Rule.

The translation covers one rule. Rule set evaluation is unchanged: processing imports, checking well-formedness, calculating the dependency graph and a stratification, the separation of run-once rules from general rules, the repeated evaluation of a stratum, and the removal of triples already in the base graph, all remain outside the translation. Use within Rule Set Evaluation shows where the translated query is used.

A SPARQL-RL processor is not required to use this translation. It is given to show the relationship between the two languages, and to show one way to evaluate rules with a SPARQL query engine.

Scope

The translation is defined over the abstract syntax: a rule is a rule head, which is a sequence of triple templates, a rule body, which is a sequence of rule elements, and the flag `rule.evaldata`.

The syntactic forms that abbreviate triples — collections, blank node property lists, reifiers and annotation blocks — are taken to have been expanded into triple patterns and triple templates by the parsing step, as they are for evaluation.

Property paths in SPARQL-RL use only `/` and `^`, both of which are SPARQL property paths. A path can be carried over unchanged, or expanded into triple patterns with fresh variables.

The output is shown in SPARQL concrete syntax. The `BASE` and `PREFIX` declarations of the rule set are copied to the query prologue. `IMPORTS` and `DATA` are features of a rule set, not of a rule, and take no part in the translation of a single rule; the triples of a data block are already in the evaluation graph when the query is executed.

The queries produced use a small part of SPARQL: basic graph patterns, `FILTER`, `BIND`, `GRAPH`, `FILTER NOT EXISTS`, a sub-`SELECT` with `GROUP BY` and the aggregates `COUNT`, `MIN`, `MAX` and `SUM`, and nested group graph patterns. There is no `OPTIONAL`, `UNION`, `MINUS` or `VALUES`, and no solution modifier on the outer query.

Inputs, Output and the Dataset

The inputs are those of evalRule(R, G, GD):

  • R, a well-formed rule;
  • G, the graph matched by the rule body when `rule.evaldata` is true; during rule set evaluation this is the evaluation graph;
  • GD, the base graph.

Recall the sense of the two flags: rule.evaldata is false for a `WHERE DATA` rule, and negation.evaldata is false for a `NOT DATA` element. In both cases, false means "match the base graph".

The output is a `CONSTRUCT` query Q, and the dataset on which Q is to be executed. Let baseRef be an IRI chosen by the translation and not used for any other purpose; this appendix writes `<urn:srl:base-graph>`.

The dataset for executing the translated query
Rule Default graph Named graph
`WHERE` — rule.evaldata is true G (baseRef, GD), and only when the rule body has a `NOT DATA` element
`WHERE DATA` — rule.evaldata is false GD none

A `WHERE DATA` rule needs no named graph. The whole rule body is matched against the base graph, so `NOT` and `NOT DATA` have the same effect: in evalRuleElements(B, SEQ, GD, GD) both branches of the negation case use GD. The translation emits no `GRAPH` for such a rule.

The graph produced by executing Q on that dataset, and the graph produced by evalRule(R, G, GD), differ only in the identity of the blank nodes created by the rule head: the two graphs are graph isomorphic. If the rule head has no blank nodes, and the rule body uses none of `BNODE`, `UUID` and `STRUUID`, the two graphs are equal.

A processor that translates every rule of a rule set against a single dataset — default graph the evaluation graph, named graph (baseRef, G0) — can keep the handling of `rule.evaldata` inside the query instead: for a `WHERE DATA` rule, enclose the whole translated body in `GRAPH baseRef { ... }`, because the active graph carries into sub-`SELECT` and `EXISTS` patterns, and translate `NOT DATA` with the `GRAPH` form in every rule. The form used in this appendix leaves the common case — a rule with no `DATA` form — as a query over a single graph.

Correspondence of Forms

The table below summarizes the translation. close is the scoping step described in Positional Scope.

Correspondence between SPARQL-RL and SPARQL
SPARQL-RL SPARQL
rule head the `CONSTRUCT` template, unchanged
triple pattern element a triple pattern in the group, unchanged
filter element FILTER(expr), in place
negation element, negation.evaldata true FILTER NOT EXISTS { inner }, then close
negation element, negation.evaldata false FILTER NOT EXISTS { GRAPH baseRef { inner } }, then close
assignment element SET(?v := expr) BIND(expr AS ?v) FILTER(BOUND(?v)), then close
group element a sub-`SELECT` with `GROUP BY`, followed by guard filters, then close
[=blank node=] in the rule body a fresh variable
[=blank node=] in the rule head unchanged: `CONSTRUCT` creates a fresh blank node for each solution
expression unchanged

Each aggregation function becomes the SPARQL aggregate of the same name, as set out in Evaluation of an Expression: `COUNT`, including the `DISTINCT` and `*` forms, `MIN`, `MAX` and `SUM`.

Positional Scope

A rule body is a sequence: each rule element transforms the solution sequence produced by the elements before it, as set out in evalRuleElements. A SPARQL group graph pattern is not read in that way. Triple patterns in a group are joined, and a `FILTER` — including a `FILTER NOT EXISTS` — applies to the solutions of the whole group it appears in, not to the part of the group written before it. `BIND` is the exception: it is positional in SPARQL as well.

The translation closes this gap with one operation. close(P) takes the sequence of SPARQL elements translated so far and replaces it with a single nested group graph pattern containing them, written `{ P }`. Elements appended after a close are joined with that group as a whole, and cannot affect a `FILTER` inside it.

Three kinds of rule element need a close; the other two do not.

Filter Elements

A filter element is left where it is written. Well-formedness requires every variable of a filter element to be in scope at that point, and every solution produced up to that point gives a value to every variable in scope (Notes on Correctness). Under that condition a filter commutes with the joins that follow it, so moving it to the end of the group — which is where SPARQL applies it — does not change the result.

Negation Elements

A negation element does not commute, because `FILTER NOT EXISTS` substitutes the bindings of the current solution into its pattern. A variable that is local to the negation element body at its position in the rule body may be given a value by a later rule element, and SPARQL would then substitute that value. 

              :c1 rdf:type :Component ;
                  :approvedBy :alice ;
                  :inTeam :t .
              :c2 rdf:type :Component ;
                  :inTeam :t .
              :t  :reviewer :rob .
            
              RULE { ?x :needsReview true }
              WHERE {
                  ?x rdf:type :Component .
                  NOT { ?x :approvedBy ?a }
                  ?x :inTeam ?t .
                  ?t :reviewer ?a .
              }
            
              CONSTRUCT { ?x :needsReview true }
              WHERE {
                  { ?x rdf:type :Component .
                    FILTER NOT EXISTS { ?x :approvedBy ?a }
                  }
                  ?x :inTeam ?t .
                  ?t :reviewer ?a .
              }
            
              :c2 :needsReview true .

At the `NOT`, the variable `?a` is local to the negation element body: the rule applies to a component with no `:approvedBy` value at all. The `?a` of `?t :reviewer ?a` is a different, later use of the same name.

The nested group graph pattern is necessary. Written as a single group, the `FILTER NOT EXISTS` is evaluated where `?a` has the value `:rob`, and the test becomes "`?x` is not approved by that reviewer" instead of "`?x` has no approver". The query would then also produce `:c1 :needsReview true`, although `:c1` is approved.

Assignment Elements

As described in Relationship between SPARQL-RL and SPARQL, `SET(?v := `expr`)` has the effect of `BIND(`expr` AS ?v)` followed by `FILTER(BOUND(?v))`: an error evaluating the expression removes the solution, rather than passing it on with `?v` unset.

The group is closed after the pair. Without the close, a solution for which the expression gave an error, and which therefore has no value for `?v`, can take a value for `?v` from a later triple pattern; the `FILTER(BOUND(?v))` at the end of the group then succeeds, and a solution that `SET` removed is restored.

Group Elements

A group element becomes a sub-`SELECT` that does not mention the variables of the enclosing group, joined into the group on the group keys. This is possible because a group element is connected to the current solution only through the keys: evalRuleElements restricts the current solution μ to GRP.keys before evaluating the group pattern, and extends μ afterwards with only the keys and the aggregation variables.

Two guard filters are placed after the sub-`SELECT`:

  • An error in an aggregate. An error calculating an aggregation function means the group is not added to the results. In SPARQL, the error leaves the aggregation variable unbound and the row is kept. A `FILTER(BOUND(?v))` for each aggregation variable whose function can give an error — `MIN`, `MAX` and `SUM`; `COUNT` cannot — gives the SPARQL-RL behavior.

  • No keys and no solutions. When there are no group keys and the group pattern has no solutions, a group element forms no groups and produces no solutions, whereas a SPARQL aggregate query without `GROUP BY` produces one solution, with `COUNT` zero and the other aggregates unbound. A fresh `(COUNT(*) AS ?n)` in the projection, with `FILTER(?n > 0)` after the sub-`SELECT`, gives the SPARQL-RL behavior. With one or more keys the two agree already: no solutions, no groups.

A group element with no aggregation assignments — the `[]` form — produces one solution for each distinct tuple of key values, and becomes `SELECT DISTINCT` over the keys.

Blank Nodes in the Rule Body

Each blank node in the rule body is replaced by a fresh variable before translation, the same variable for each occurrence of the same blank node, as described by treating blank nodes as variables.

The translation has a second reason to make the replacement: close divides the rule body between several basic graph patterns, and SPARQL does not allow the same blank node label to be used in two different basic graph patterns.

Translation Algorithm

The algorithm uses the component names of Elements of the Abstract Syntax. It also uses:

  • a source of fresh variables, which are different from each other and from every variable occurring in the rule;
  • baseRef, the IRI for the named graph holding the base graph, or none when the rule is a `WHERE DATA` rule;
  • a group graph pattern under construction, held as a sequence of elements — triple patterns, filters, `BIND`s, nested groups and sub-`SELECT`s. Writing the sequence between `{` and `}` gives the SPARQL syntax. 
define translateRule(R):
    where
        R is a well-formed rule
    # The result is a SPARQL CONSTRUCT query, executed on the dataset
    # given in the table of section "Inputs, Output and the Dataset".

    let B be R.body, treating blank nodes as variables

    if R.evaldata:
        let bg = baseRef
    else:
        # The default graph is GD, so NOT DATA needs no GRAPH.
        let bg = none
    endif

    let W = translateBody(B, bg)
    let T = translateTemplate(R.head)

    the result is the query:  CONSTRUCT { T } WHERE { W }
enddefine

define translateBody(B, bg):
    where
        B is a sequence of rule elements
        bg is an IRI, or none
    # The result is a SPARQL group graph pattern.

    let P be the empty sequence

    foreach rule element rElt in B:

        if rElt is a triple pattern element TP:
            append TP to P
        endif

        if rElt is a filter element F:
            append FILTER( F.expr ) to P
        endif

        if rElt is a negation element N:
            let P1 = translateBody(N.inner, bg)
            if N.evaldata is false and bg is not none:
                let P1 = GRAPH bg { P1 }
            endif
            append FILTER NOT EXISTS { P1 } to P
            P = close(P)
        endif

        if rElt is an assignment element A:
            append BIND( A.expr AS A.var ) to P
            append FILTER( BOUND( A.var ) ) to P
            P = close(P)
        endif

        if rElt is a group element GRP:
            let (SUB, GUARDS) = translateGroup(GRP, bg)
            append { SUB } to P
            foreach filter F in GUARDS:
                append F to P
            endfor
            P = close(P)
        endif

    endfor
    the result is P
enddefine

define close(P):
    # Fix the scope of P.  The elements of P become one nested group
    # graph pattern; elements appended afterwards join with the group
    # as a whole and do not affect the filters inside it.
    the result is the sequence of one element:  { P }
enddefine

define translateGroup(GRP, bg):
    where
        GRP is a group element
        bg is an IRI, or none
    # The result is a pair: a sub-SELECT, and a sequence of guard
    # filters to be placed immediately after it.

    let P1 = translateBody(GRP.pattern, bg)

    let PROJ be the empty sequence
    let GUARDS be the empty sequence

    foreach variable k in GRP.keys:
        append k to PROJ
    endfor

    foreach aggregation assignment AG in GRP.aggregations:
        append ( sparqlAggregate(AG.function) AS AG.var ) to PROJ
        if AG.function is one of MIN, MAX, SUM:
            # An error calculating an aggregate removes the group.
            # In SPARQL, AG.var is left unbound.  COUNT cannot error.
            append FILTER( BOUND( AG.var ) ) to GUARDS
        endif
    endfor

    if GRP.keys is empty:
        # A group element produces no solutions when the group pattern
        # has no solutions; a SPARQL aggregate without GROUP BY
        # produces one solution.  This also covers the case of
        # GRP.aggregations being empty.
        let n be a fresh variable
        append ( COUNT(*) AS n ) to PROJ
        append FILTER( n > 0 ) to GUARDS
        let SUB = SELECT PROJ WHERE { P1 }
    else if GRP.aggregations is empty:
        let SUB = SELECT DISTINCT PROJ WHERE { P1 }
    else:
        let SUB = SELECT PROJ WHERE { P1 } GROUP BY GRP.keys
    endif

    the result is (SUB, GUARDS)
enddefine

translateTemplate(H) writes the rule head H as a `CONSTRUCT` template. Variables, IRIs and literals are unchanged; blank nodes are unchanged; a template for a [=triple term=] is written as a SPARQL triple term. No other adjustment is needed:

  • well-formedness requires every variable of the rule head to be in scope at the end of the rule body, and every solution gives a value to every variable in scope, so the `CONSTRUCT` rule that skips an instantiation containing an unbound variable never applies;
  • `CONSTRUCT` replaces the blank nodes of the template with fresh blank nodes once for each solution, which is replaceBlankNodes applied for each solution in evalRule;
  • both evalRule and `CONSTRUCT` produce a set of triples.

Examples

In the examples, the prologue of the query is not shown. Unless stated otherwise, the query is executed with the graph matched by the rule body as the default graph. 

            RULE { ?x :status :criticallyExposed }
            WHERE {
                ?x :exposedTo ?v .
                ?v :severity ?s .
                FILTER(?s >= 9.0)
            }
          
            CONSTRUCT { ?x :status :criticallyExposed }
            WHERE {
                ?x :exposedTo ?v .
                ?v :severity ?s .
                FILTER(?s >= 9.0)
            }

A rule body of triple pattern elements and filter elements translates directly. 

            RULE  { ?x :distanceKilometers ?kilometers }
            WHERE {
                ?x :distanceMiles ?miles .
                NOT DATA { ?x :distanceKilometers ?km }
                SET ( ?kilometers := xsd:integer(?miles * 1.60934))
            }
          
            CONSTRUCT { ?x :distanceKilometers ?kilometers }
            WHERE {
                { ?x :distanceMiles ?miles .
                  FILTER NOT EXISTS {
                      GRAPH <urn:srl:base-graph> { ?x :distanceKilometers ?km }
                  }
                }
                BIND( xsd:integer(?miles * 1.60934) AS ?kilometers )
                FILTER( BOUND(?kilometers) )
            }

This query is executed with the evaluation graph as the default graph and the base graph as the named graph `<urn:srl:base-graph>`. The inner group graph pattern is the close after the negation element; the close after the assignment element encloses the whole `WHERE` clause and is not written (Simplifications).

The same rule written with `WHERE DATA` translates to the same query without the `GRAPH` form, executed with the base graph as the default graph: 

            RULE  { ?x :distanceKilometers ?kilometers }
            WHERE DATA {
                ?x :distanceMiles ?miles .
                NOT { ?x :distanceKilometers ?km }
                SET ( ?kilometers := xsd:integer(?miles * 1.60934))
            }
          
            CONSTRUCT { ?x :distanceKilometers ?kilometers }
            WHERE {
                { ?x :distanceMiles ?miles .
                  FILTER NOT EXISTS { ?x :distanceKilometers ?km }
                }
                BIND( xsd:integer(?miles * 1.60934) AS ?kilometers )
                FILTER( BOUND(?kilometers) )
            }
          
            RULE { ?x :vulnerabilityCount ?n ;
                      :maxSeverity ?m }
            WHERE {
                ?x rdf:type :Component .
                GROUP BY ?x { ?x :exposedTo ?v . ?v :severity ?s }
                    [ ?n := COUNT(*) , ?m := MAX(?s) ]
            }
          
            CONSTRUCT { ?x :vulnerabilityCount ?n ;
                           :maxSeverity ?m }
            WHERE {
                ?x rdf:type :Component .
                { SELECT ?x (COUNT(*) AS ?n) (MAX(?s) AS ?m)
                  WHERE { ?x :exposedTo ?v . ?v :severity ?s }
                  GROUP BY ?x
                }
                FILTER( BOUND(?m) )
            }

`?m` is guarded because `MAX` can give an error; `?n` is not, because `COUNT` cannot. A component with no matching `:exposedTo` triple forms no group, and so produces no triples, in the rule and in the query alike. 

            RULE { :deployment :exposureCount ?n }
            WHERE {
                GROUP { ?x :exposedTo ?v } [ ?n := COUNT(*) ]
            }
          
            CONSTRUCT { :deployment :exposureCount ?n }
            WHERE {
                { SELECT (COUNT(*) AS ?n) (COUNT(*) AS ?g0)
                  WHERE { ?x :exposedTo ?v } }
                FILTER( ?g0 > 0 )
            }

`?g0` is a fresh variable. Without the guard, the query produces `:deployment :exposureCount 0` when there are no matches, where the rule produces nothing. In this case the guard could use `?n`, since a `COUNT(*)` is already in the projection. 

            RULE { [] rdf:type :Notification ; :concerns ?x }
            WHERE { ?x :status :criticallyExposed }
          
            CONSTRUCT { [] rdf:type :Notification ; :concerns ?x }
            WHERE { ?x :status :criticallyExposed }

A rule with a blank node in the rule head is a run-once rule. That is a matter for rule set evaluation, not for the translation: each execution of the query creates new blank nodes.

Notes on Correctness

The translation rests on two properties of a well-formed rule.

First, solutions are total over the variables in scope. If each solution of the incoming solution sequence gives a value to each of the initial variables, then after the i-th rule element each solution of evalRuleElements gives a value to each variable of vars(S, i, V0). This follows by induction over the cases of evalRuleElements: a triple pattern element gives a value to each of its variables in every match; an assignment element either gives a value to its variable or removes the solution; a group element gives values to the keys and to the aggregation variables; a filter element and a negation element give values to no variables and either keep or remove a whole solution.

Second, filters can be moved. If every solution of a pattern A gives a value to every variable of an expression F, then Filter(F, Join(A, B)) and Join(Filter(F, A), B) have the same solutions. With the first property, and the well-formedness condition on filter elements, a translated `FILTER` can be left where it is written.

The two properties give the following, by induction over the rule body. Let Pi be the pattern built by translateBody after the first i rule elements, with any group still being built closed. The solutions of Pi, evaluated on the dataset of Inputs, Output and the Dataset, are the solutions of evalRuleElements after the i-th rule element, with the same multiplicities.

  • Triple pattern element: matching a basic graph pattern on the active graph is graphMatch, and forming a group is the join of compatible solutions used by evalRuleElements.
  • Filter element: by the second property above.
  • Negation element: after the close, the `FILTER NOT EXISTS` is applied to the solutions of the translated prefix and to no others. For each such solution μ, SPARQL substitutes the values of μ into the inner pattern and tests it against the active graph; for a pattern of triple patterns, filters and `GRAPH`, that is evalRuleElements(N.inner, { μ }, ·, GD) being empty. Variables local to the negation element body have no value in μ, are not substituted, and cannot be given a value later because the group is closed.
  • Assignment element: `BIND` is positional in SPARQL, and the `FILTER(BOUND(...))` inside the closed group removes exactly the solutions for which the expression gave an error.
  • Group element: the members of the group with a given tuple of key values do not depend on the rest of the current solution, because evalRuleElements evaluates the group pattern from the current solution restricted to the keys. The sub-`SELECT` calculates those groups, one solution for each; joining on the keys selects, for each current solution, the groups compatible with it, which is the result of merge in evalRuleElements. A key that is in scope outside the group element but does not occur in the group pattern has no value in the sub-`SELECT` solution, and so joins with every current solution, which is again the single group formed by evalRuleElements. The guard filters account for the two remaining differences (Group Elements).

For the rule head, `CONSTRUCT` instantiates the template for each solution, with fresh blank nodes for each solution, and collects the triples as a set. That is subst applied to replaceBlankNodes of the head, for each solution, as in evalRule. The identity of the new blank nodes is the one difference, which is why the two graphs are graph isomorphic rather than equal.

Simplifications

The algorithm is written so that every case is handled in the same way. A translation can apply any of the following without changing the result.

  • Remove the last close. The group made by the last negation element, assignment element or group element encloses the whole `WHERE` clause; `WHERE { { P } }` is `WHERE { P }`.
  • Omit a close when nothing later is affected by it. A close is needed only when a later element of the same sequence can give a value to a variable that one of the filters depends on: for a negation element, a variable of the negation element body that is not in scope at that point; for an assignment element or a group element, a guarded variable that occurs later. In particular, a group element whose translation has no guard filters needs no close.
  • Use an existing `COUNT(*)` for the guard on a group element with no keys, instead of projecting a fresh one.
  • Flatten a group that contains only another group.
  • Use a dataset of one graph when the rule has no `DATA` form; the query then has no `GRAPH` form.

Use within Rule Set Evaluation

A translated query replaces evalRule in Evaluation of a Rule Set. Nothing else in that algorithm changes. Each rule is translated once, after preparation; the query is then executed again for each round of the stratum, with only the dataset changing as the evaluation graph grows. 

# After preparation, translate each rule once.
foreach rule R in RS.rules:
    let Q[R] = translateRule(R)
endfor

# In the evaluation of a stratum, replace
#     let X = evalRule(R, GE, G0)
# with:
    if R.evaldata:
        let DS be the dataset with default graph GE,
            together with the named graph (baseRef, G0)
            if Q[R] uses baseRef
    else:
        let DS be the dataset with default graph G0
    endif
    let X = the graph produced by executing Q[R] on DS
# and continue as before:
    let Y = { t ∈ X | t ∉ GE }
    GI = GI ∪ Y
    GE = GE ∪ Y

Two points from Relationship between SPARQL-RL and SPARQL are the responsibility of the process that executes the queries, not of the translation.

  • `NOW()` is fixed for one SPARQL query execution, but is defined in SPARQL-RL to give the same point in time throughout a rule set evaluation. Either the query engine is given the fixed value, or the translation replaces `NOW()` by a constant.
  • Blank nodes in the rule head, and `BNODE`, `UUID` and `STRUUID`, produce new terms on each execution of the query. Rules that use them are run-once rules, and the stratification, not the translation, is what stops them being executed again.

Open Points

subst(μ, TT) in evalRule can produce something that is not an RDF triple — a literal in the subject position, a literal or blank node in the predicate position, or a triple term in the subject position — when a variable has such a value. SPARQL `CONSTRUCT` passes over such an instantiation; Evaluation of a Rule adds it. The specification needs to say which happens. The translation has the `CONSTRUCT` behavior.

The guard for a group element with no group keys follows Evaluation of a Rule as written: no solutions of the group pattern means no groups and no solutions. If the Working Group decides instead to follow SPARQL, which produces one solution with `COUNT` zero, the guard is removed.

The guards `FILTER(BOUND(...))` on the aggregation variables follow the editorial note in Evaluation of an Expression, that an error in calculating an aggregate means the group is not added to the results. They should follow whatever that note becomes.

Well-formedness allows a group pattern to use a variable that is in scope outside the group element and is not a group key, but evaluation restricts the current solution to the keys, so such a variable behaves as if it were local to the group pattern. The sub-`SELECT` translation depends on that, and is correct either way; the well-formedness condition could be made to match evaluation by taking the initial variables of the group pattern to be the group keys that are in scope.

The translation depends on the way SPARQL evaluates `EXISTS`, by substituting the current solution into the pattern, and uses it only over triple patterns, filters and `GRAPH`, which is the whole of a negation element body.
