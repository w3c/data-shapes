This document contains draft text for an appendix "Translation of SPARQL-RL Text to SPARQL" of SPARQL 1.2 RL.

It gives a second translation of a SPARQL-RL rule into a SPARQL `CONSTRUCT` query. The companion appendix (Translation of SPARQL-RL to SPARQL) defines the translation on the abstract syntax; the translation here starts from the concrete syntax of a `RULE`, as accepted by the grammar, and produces the text of a query. The two produce the same query.

This document is not a W3C publication. It is working material for the W3C Data Shapes Working Group, addressing issue #1303.

Translation of SPARQL-RL Text to SPARQL

The appendix Translation of SPARQL-RL to SPARQL defines a translation of one rule to one `CONSTRUCT` query on the abstract syntax: it assumes a parser has reduced the rule to triple patterns and rule elements, and builds the query structurally. This appendix gives the same translation one level earlier: from the text of a `RULE`, as accepted by the grammar, to the text of a SPARQL 1.2 query. It is the form of the translation suited to a source-to-source tool — a preprocessor that rewrites rule text into query text and has no SPARQL machinery of its own.

The two translations produce the same query, executed over the same dataset (), so everything established for the first — the scoping device, the guard filters, the dataset convention, and correctness against evalRule (Evaluation of a Rule) — carries over and is not restated here.

Transcription

The translation is a transcription, not a reconstruction. The SPARQL-RL grammar is derived from the SPARQL 1.2 grammar, and everything a rule says about triples and values — head templates, body triple patterns with reifiers, annotations and triple terms, property paths, filter expressions, literals, escapes — is written in productions that are also SPARQL 1.2 productions, with the same meaning. The default action is therefore to copy the source text unchanged, and the algorithm consists of the places where that default is wrong:

Rewrite points; all other text is copied
Source form Emitted text
`BASE` and `PREFIX` declarations in force copied, in order
`RULE` iri? `{` H `} WHERE` `CONSTRUCT {` H `} WHERE` — the iri survives only as a comment
`WHERE DATA` `WHERE`; the query's default graph becomes the base graph
a body triples block copied — except each labeled [=blank node=] becomes a variable ()
`FILTER` C copied, in place
`NOT {` P `}` `FILTER NOT EXISTS {` P′ `}`, then close
`NOT DATA {` P `}` `FILTER NOT EXISTS { GRAPH` baseRef `{` P′ `} }`, then close
`SET ( ?v :=` e `)` `BIND(` e `AS ?v ) FILTER( BOUND(?v) )`, then close
`GROUP BY` keys `{` P `} [` assignments `]` a sub-`SELECT` with `GROUP BY`, guard filters, then close
the head template `{` H `}` copied

close is the scoping device of the companion appendix (Positional Scope), here as a text operation: wrap everything emitted so far for the current group in `{` ... `}`. The guard filters on a group element and the `BOUND` test after a `BIND` are likewise those of the companion appendix.

Inputs, Output and Preconditions

The inputs are:

  • R, the parse tree of one rule — production Rule ::= 'RULE' iri? HeadTemplate 'WHERE' 'DATA'? BodyPattern;
  • PRO, the `BaseDecl` and `PrefixDecl` nodes in force at R: those textually preceding it in the rule set, in source order;
  • baseRef, an IRI chosen by the translation, written `<urn:srl:base-graph>` in this appendix.

The rule set parses, and R is a well-formed rule. Working at the text level does not remove the well-formedness check: well-formedness is what allows a `FILTER` to stay where it is written and makes the emitted `BIND` legal SPARQL. The check is defined on structure the parse tree already carries.

The output is the text of a `CONSTRUCT` query, and a flag needsBase saying whether the query mentions baseRef. The dataset for executing the query is that of the companion appendix (Inputs, Output and the Dataset): for an ordinary rule, the default graph is the evaluation graph, with the named graph (baseRef, GD) when needsBase; for a `WHERE DATA` rule, the default graph is the base graph and there is no named graph.

The translation works on a parse tree rather than as a stream editor because two of the rewrites reorder text: `SET ( ?v := e )` moves the variable and the expression around `AS`, and a `GROUP` element moves the aggregation assignments from after the group pattern into a projection before it, writing the keys twice. close wraps text already emitted. The translator therefore buffers one rule. The tree walk is shallow: the tree is used only down to the productions named in , and everything below them is handled as text.

Spans, Tokens and Fresh Names

The span of a parse tree node is the source text from its first token to its last, including the original white space between them. Comments are white space in both languages and may ride along inside a span; a comment always ends with a line break lying between the same two tokens, so a span never ends in mid-comment. When the translator emits tokens of its own next to a span, a single space is always a sufficient separator. 

define copy(node):
    # The default action.
    the result is span(node)
enddefine

define copyPattern(node):
    # copy, for pattern text: blank node labels become variables.
    the result is span(node) in which the text of each BLANK_NODE_LABEL
        token "_:label" is replaced by bnodeVar(label)
    # The replacement is by token: the characters "_:" inside an IRI or
    # a string literal are not a BLANK_NODE_LABEL token, and are not
    # touched.  ANON "[]", blank node property lists "[ ... ]" and
    # collections "( ... )" are not rewritten.
enddefine

Let V be the set of variable names occurring in R — every `VAR1` and `VAR2` token, without its `?` or `$` — extended as names are generated. 

define freshVar():
    let name be the next name of the form "_t0", "_t1", ... not in V
    add name to V
    the result is "?" + name
enddefine

define bnodeVar(label):
    # Same label, same variable, across the whole rule body.
    if BMAP[label] is not defined:
        BMAP[label] = freshVar()
    endif
    the result is BMAP[label]
enddefine

The variable name is generated by counter, not derived from the label text: a blank node label (`BLANK_NODE_LABEL`) may contain `-` and `.`, which a variable name (`VARNAME`) cannot.

BMAP is per rule and applies to the rule body only. Blank nodes in the head template are copied unchanged: a `CONSTRUCT` template blank node is instantiated fresh for each solution, which is replaceBlankNodes applied per solution. A label that appears in both head and body is thereby decoupled, matching evaluation, where body blank nodes are variables (treating blank nodes as variables) and head blank nodes are template blank nodes.

Translation Algorithm

# State per rule: V and BMAP (previous section), and
let needsBase = false

define trRuleText(R, PRO):
    # R   : parse tree of 'RULE' iri? HeadTemplate 'WHERE' 'DATA'? BodyPattern
    # PRO : BaseDecl and PrefixDecl nodes in force at R, in source order
    let out = empty text

    foreach declaration D in PRO:
        append copy(D) and a line break to out
    endfor

    if R has an iri:
        append "# RULE " copy(the iri) and a line break to out   # comment only
    endif

    if R has the DATA token:        # a WHERE DATA rule
        let bg = none               # default graph will be GD;
                                    # NOT and NOT DATA coincide, no GRAPH
    else:
        let bg = baseRef
    endif

    append "CONSTRUCT " copy(R.HeadTemplate) to out      # braces included
    append " WHERE { " trPatternText(items of R.BodyPattern, bg) " }" to out

    the result is (out, needsBase)
enddefine

define trPatternText(ITEMS, bg):
    # ITEMS: the children of a BodyPattern, a NegationPattern, or a
    # GroupPattern, in source order -- triples blocks interleaved with
    # Filter / Negation / Assignment / GroupAggregate nodes (the grammar
    # limits which of these occur in which production).
    # The optional "." token between items is not copied.
    let out = empty text

    foreach item X in ITEMS:

        if X is a BodyTriplesBlock:
            append copyPattern(X) to out
        endif

        if X is a Filter:                     # 'FILTER' Constraint
            append copy(X) to out             # verbatim, in place
        endif

        if X is a Negation:                   # 'NOT' 'DATA'? '{' P '}'
            let inner = trPatternText(items of X.NegationPattern, bg)
                # the grammar allows only triples blocks and filters here
            if X has the DATA token and bg is not none:
                inner = "GRAPH " bg " { " inner " }"
                needsBase = true
            endif
            append "FILTER NOT EXISTS { " inner " }" to out
            out = "{ " out " }"                            # close
        endif

        if X is an Assignment:                # 'SET' '(' Var ':=' Expression ')'
            append "BIND( " copy(X.Expression) " AS " copy(X.Var) " )" to out
            append "FILTER( BOUND(" copy(X.Var) ") )" to out
            out = "{ " out " }"                            # close
        endif

        if X is a GroupAggregate:
            append trGroupText(X, bg) to out
            out = "{ " out " }"                            # close
        endif

    endfor
    the result is out
enddefine

define trGroupText(X, bg):
    # X: 'GROUP' ( 'BY' ListVars )? '{' GroupPattern '}'
    #        ( ANON | '[' AggregationAssignments ']' )
    # AggregationAssignments ::= ( AggregationAssignment ( ',' AggregationAssignment )* )?
    # AggregationAssignment  ::= Var ':=' AggregationFunction

    let keys = the Var tokens of ListVars, keeping the first occurrence
               of each variable and dropping repeats
        # ListVars is Var+, so a variable may be written twice;
        # SPARQL does not allow a variable to be projected twice.

    let inner = trPatternText(items of X.GroupPattern, bg)
        # the grammar allows triples blocks, filters and assignments here

    let PROJ be the empty text
    let GUARDS be the empty text
    foreach k in keys:
        append copy(k) to PROJ
    endfor
    foreach aggregation assignment A in X, in source order:
        append "( " copy(A.AggregationFunction) " AS " copy(A.Var) " )" to PROJ
            # the aggregation function text -- COUNT(*), COUNT(DISTINCT ?x),
            # MIN(?x), MAX(?x), SUM(?x) -- is SPARQL text already
        if A.AggregationFunction is a MIN, MAX or SUM form:
            # An error calculating an aggregate removes the group;
            # COUNT cannot raise an error.
            append "FILTER( BOUND(" copy(A.Var) ") )" to GUARDS
        endif
    endfor

    if keys is empty:
        # No solutions of the group pattern must mean no solutions;
        # a SPARQL aggregate query without GROUP BY returns one row.
        let n = freshVar()
        append "( COUNT(*) AS " n " )" to PROJ
        append "FILTER( " n " > 0 )" to GUARDS
        the result is "{ SELECT " PROJ " WHERE { " inner " } } " GUARDS

    else if X has no aggregation assignments:        # ANON "[]", or "[ ]"
        the result is "{ SELECT DISTINCT " PROJ " WHERE { " inner " } }"

    else:
        the result is "{ SELECT " PROJ " WHERE { " inner " } GROUP BY "
                      each key of keys " } " GUARDS
    endif
enddefine

Verbatim Copying

A verbatim copy is justified region by region: in each case the SPARQL-RL productions are, by construction, a subset of the SPARQL 1.2 productions with the same meaning, so the SPARQL parse of the copied text yields the same patterns that the SPARQL-RL parse yields.

  • Head templates (`HeadTemplate` and below): the SPARQL 1.2 construct template productions, without paths. Variables, reified triple blocks, annotation blocks, collections and templates for a [=triple term=] carry over; blank nodes mean "fresh for each solution" in both languages.
  • Body triples blocks (`BodyTriplesBlock` and below): the SPARQL 1.2 triples block productions — including `~` reifiers, `{| |}` annotation blocks, `<<( )>>` triple terms, `a`, collections and blank node property lists — with the one exception below.
  • Paths (`VerbPath`, `Path`): SPARQL-RL allows only `/`, `^`, `( )`, `a` and IRIs, all of which are SPARQL paths. SPARQL's own translation of `/` and `^` expands them to the same triple patterns with fresh variables that the SPARQL-RL abstract syntax uses.
  • Filters and expressions (`Filter`, `Constraint`, `Expression` and below): the SPARQL expression grammar minus features — there is no `EXISTS`, `BOUND`, `COALESCE`, `RAND` and no hash functions. Removals only, so every SPARQL-RL expression is a SPARQL expression, including the SPARQL 1.2 additions such as `LANGDIR`, `hasLANG`, `STRLANGDIR` and triple terms in expressions.
  • Terminals: IRIs, prefixed names, literals, language tags, escapes, variables and comments are the SPARQL 1.2 terminals.

The exception is the labeled blank node in a rule body. In SPARQL-RL text, a label is a rule-wide name: it may be reused across triples blocks, across a `SET`, and between the outer body and a `NOT` body, and evaluation reads every occurrence as the same variable. SPARQL does not allow a blank node label to be used in two different basic graph patterns, and this translation manufactures exactly such boundaries. Both of the following are syntax errors in SPARQL: 

    { { _:b :p ?x } _:b :q ?z }                        # a close boundary
    { _:b :p ?x FILTER NOT EXISTS { _:b :q ?z } }      # a negation

Replacing every `BLANK_NODE_LABEL` token with its variable makes the text legal and gives each occurrence the rule-wide variable reading that SPARQL-RL requires.

The anonymous forms stay. An `[]`, a `[` ... `]` property list, or a `(` ... `)` collection is a single syntactic node, so it can never straddle an inserted boundary — the boundaries fall only between the items of a pattern — and within one basic graph pattern SPARQL already treats its blank node as a fresh, unprojected variable, which is the SPARQL-RL reading.

Agreement with the Abstract-Syntax Translation

For a well-formed rule R, parsing the text produced here yields the query that the abstract-syntax translation produces from the parse of R — up to the names of translator-introduced variables, and up to when syntactic sugar is expanded. Correctness against evalRule then follows from the companion appendix, and nothing semantic needs to be re-established. The claim holds clause by clause:

  • each copy clause copies a region whose SPARQL parse produces the same triple patterns, templates, paths or expression that the SPARQL-RL parse produces — the same productions, the same expansions of collections, property lists, reifiers and annotations, and the same expansion of `/` and `^` paths;
  • copyPattern performs, at the token level, treating blank nodes as variables, restricted to labels, with the previous section justifying leaving the anonymous forms to SPARQL;
  • each rewrite clause emits text whose parse is the corresponding output form of the companion appendix: the `FILTER NOT EXISTS` with its optional `GRAPH`, the `BIND`–`BOUND` pair, the sub-`SELECT` with its guards, and the same close nesting, since both translations close after the same three kinds of element;
  • trRuleText assembles the same `CONSTRUCT { head } WHERE { body }` under the same dataset convention, with needsBase true exactly when a `NOT DATA` was translated inside an ordinary rule.

Examples

The copied `BASE` and `PREFIX` declarations are not shown, and the final close, which would wrap the whole `WHERE` clause, is elided (Simplifications). 

            RULE  { ?x :distanceKilometers ?kilometers }
            WHERE {
                ?x :distanceMiles ?miles .
                NOT DATA { ?x :distanceKilometers ?km }
                SET ( ?kilometers := xsd:integer(?miles * 1.60934))
            }
          
            CONSTRUCT { ?x :distanceKilometers ?kilometers }
            WHERE {
                { ?x :distanceMiles ?miles .
                  FILTER NOT EXISTS {
                      GRAPH <urn:srl:base-graph> { ?x :distanceKilometers ?km }
                  }
                }
                BIND( xsd:integer(?miles * 1.60934) AS ?kilometers )
                FILTER( BOUND(?kilometers) )
            }

The head and the first triples block are copied; the `NOT DATA` and the `SET` are rewritten, the expression inside the `SET` again copied; needsBase is true. The emitted text is flat — the layout above is cosmetic. 

            RULE { ?x :vulnerabilityCount ?n ;
                      :maxSeverity ?m }
            WHERE {
                ?x rdf:type :Component .
                GROUP BY ?x { ?x :exposedTo ?v . ?v :severity ?s }
                    [ ?n := COUNT(*) , ?m := MAX(?s) ]
            }
          
            CONSTRUCT { ?x :vulnerabilityCount ?n ;
                           :maxSeverity ?m }
            WHERE {
                ?x rdf:type :Component .
                { SELECT ?x (COUNT(*) AS ?n) (MAX(?s) AS ?m)
                  WHERE { ?x :exposedTo ?v . ?v :severity ?s }
                  GROUP BY ?x
                }
                FILTER( BOUND(?m) )
            }

The key `?x` is written twice, in the projection and in the `GROUP BY`; the aggregation assignments move from after the group pattern into the projection before it; the function and variable texts are copies. 

            RULE { ?x :unreviewed true }
            WHERE {
                ?x :exposedTo _:v .
                NOT { _:v :reviewedBy ?r }
            }
          
            CONSTRUCT { ?x :unreviewed true }
            WHERE {
                ?x :exposedTo ?_t0 .
                FILTER NOT EXISTS { ?_t0 :reviewedBy ?r }
            }

The label `_:v` becomes the variable `?_t0` at both occurrences: it is bound by the first triple pattern and substituted into the `NOT EXISTS`, which is the SPARQL-RL reading of the label. Copied unchanged, the text would not even parse as SPARQL. An anonymous form such as `?x :exposedTo [ :severity ?s ]` in the same body would be copied unchanged.

The rule and query file pairs listed in the companion appendix serve this translation equally: for each pair, the query text is a transcription of the rule text in the sense of this appendix.

Details of the Text Level

  • Dots. The optional `.` between pattern items is not copied; the dots inside a copied triples block, including a trailing one, are part of the span and are legal where they land.
  • Duplicate keys. `ListVars` is `Var+`, so `GROUP BY ?x ?x` parses; the projection and the `GROUP BY` emit each key once.
  • The rule's iri has no counterpart in a query and survives only as a comment.
  • Prologue. The declarations in force are copied in order; both languages apply repeated `BASE` and `PREFIX` declarations sequentially, so redeclaration between rules carries over. If the rule text uses a relative IRI with no `BASE` in force, the query must be executed with the rule set's base, or the translator prepends a `BASE` declaration giving it. The SPARQL-RL `VERSION` declaration versions the rules language, not SPARQL, and is not copied. Pruning unused prefixes is cosmetic.
  • Aggregation assignments are read from the parse tree; their separating commas are punctuation only, and an empty `[ ]` means the same as the ANON form `[]`.
  • Output form. The emitted text is flat; pretty-printing is cosmetic. The simplifications of the companion appendix apply unchanged — eliding the final close, omitting a close that nothing later can disturb, reusing an existing `COUNT(*)` for the no-keys guard, flattening a group of one group, and the single-graph dataset when the rule has no `DATA` form.

Notes

The driver-side points of the companion appendix (Use within Rule Set Evaluation) are unchanged: the query is produced once and re-executed each round with the dataset re-pointed; `NOW()` is pinned across the rule set evaluation by the engine or by substituting a constant; and rules that create fresh RDF terms are run-once rules, which the stratification keeps from being executed again. The open points recorded there apply to this translation verbatim.

One observation belongs to the concrete syntax. SPARQL-RL places no restriction on reusing a blank node label across triples blocks or into a negation body — the label is a rule-wide variable — where SPARQL and Turtle forbid the corresponding reuse. That asymmetry is what makes the label substitution of this appendix mandatory. The specification could state the intended scope of blank node labels explicitly, so that implementers of a text-level translator do not assume the SPARQL rule.
